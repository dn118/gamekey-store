# GameKey Store

Тестовый магазин цифровых товаров. Проект показывает не только витрину, но и надёжную однократную выдачу ключа при повторных и параллельных событиях оплаты.

## Что реализовано

- верхняя часть витрины по макету: шапка, поиск, карусель, сервисы, Steam-пополнение и ряд карточек;
- все пять интерактивов: карусель, выпадающий каталог, валюты, hover сервисов и hover карточек;
- создание заказа со стабильным `client_token`, защищающим двойной клик и повтор запроса после обрыва связи;
- эмуляция успешной и неуспешной оплаты;
- идемпотентный REST-вебхук оплаты;
- однократная выдача из пула ключей;
- рабочая покупка для всех пяти карточек витрины;
- два поставщика-заглушки A/B с настраиваемыми ошибками, задержкой и таймаутами;
- восстановимые состояния `out_of_stock` и `delivery_failed`;
- страница статуса заказа и минимальная админка `/admin`;
- промокоды с конкурентно-безопасным лимитом применений;
- автоматический состязательный сценарий: 50 параллельных вебхуков, повтор `event_id`, ранний вебхук, `LIMIT3` и восстановление пустого пула.

## Стек

- TypeScript, React/Vinext;
- REST API на Cloudflare Worker-compatible Node.js runtime;
- Cloudflare D1 (SQLite) и Drizzle migrations;
- CSS без отдельной UI-темы; базовые доступные примитивы используются только для диалога, кнопок, полей и таблицы.

## Запуск локально

Требуется Node.js `>=22.13.0`.

```bash
npm run install:ci
npm run db:local
npm run dev
```

После запуска откройте адрес, показанный Vite. Витрина доступна на `/`, админка — на `/admin`.

Проверка сборки:

```bash
npm test
```

## Проверка гонок

Локальный воспроизводимый прогон использует изолированную D1-базу и не требует отдельного сервера:

```bash
npm run test:race
```

Для проверки уже запущенной версии: `BASE_URL=https://example.com npm run test:race:remote`.

Скрипт проверяет:

1. 50 разных параллельных событий `paid` по одному заказу расходуют ровно один ключ.
2. 20 параллельных повторов одного `event_id` ничего не меняют.
3. Вебхук до создания заказа сохраняется и обрабатывается после появления заказа.
4. `LIMIT3` при десяти параллельных заказах применяется ровно три раза.
5. Пустой пул даёт `out_of_stock`, после пополнения ручная повторная выдача выдаёт ровно один ключ.

Тестовый служебный endpoint изменения состояния требует переменную окружения `TEST_ADMIN_TOKEN` и такой же токен в заголовке `x-admin-token`. Секрет не хранится в репозитории.

## Почему ключ выдаётся один раз

Защита сделана на уровне базы, а не только JavaScript-проверками:

- `orders.client_token` уникален — повтор создания возвращает существующий заказ;
- `payment_events.event_id` является первичным ключом — повтор события не создаёт новый факт оплаты;
- endpoint вебхука сначала надёжно сохраняет событие, сразу отвечает `200 OK`, а обработку продолжает в фоне;
- переход заказа в `delivering` выполняется условным атомарным `UPDATE ... WHERE status IN (...)`;
- ключ резервируется одним `UPDATE ... RETURNING` только из свободных записей;
- `inventory_keys.assigned_order_id` и `assigned_request_id` имеют уникальные ограничения;
- `orders.code` также уникален;
- после таймаута повторяется тот же `request_id`, поэтому поставщик возвращает ранее закреплённый код.

Даже если две операции одновременно прошли предварительные проверки, ограничения базы не позволят закрепить два ключа за одним заказом или один ключ за двумя заказами.

## Вебхуки раньше заказа и не по порядку

Каждый вебхук сначала сохраняется в `payment_events`. Если заказа ещё нет, событие остаётся необработанным. После создания заказа выполняется reconciliation всех ожидающих событий. Статус `paid` считается необратимым: последующее или запоздавшее `failed` не отменяет уже подтверждённую оплату и выдачу.

## Таймаут поставщика

Таймаут не считается доказанным отказом. Поставщик мог закрепить код до потери ответа. Поэтому приложение сначала повторяет запрос к тому же поставщику с тем же `request_id`. На резервного поставщика оно переключается только после явного отказа или подтверждённого отсутствия товара. Дополнительную защиту даёт уникальность `assigned_order_id`.

## Основные endpoints

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/api/orders` | создать заказ |
| `GET` | `/api/orders/:id` | статус и диагностика |
| `POST` | `/api/orders/:id/pay` | эмуляция оплаты |
| `POST` | `/api/webhooks/payment` | контракт платёжного вебхука |
| `POST` | `/api/providers/:provider/issue` | контракт поставщика A/B |
| `GET` | `/api/admin/recovery` | оплаченные, но невыданные заказы |
| `POST` | `/api/admin/orders/:id/retry` | безопасная повторная выдача |
| `POST` | `/api/admin/inventory` | пополнить пул ключей |
| `POST` | `/api/admin/providers` | настроить ошибки/таймауты поставщика |

## Время

Фактическое время разработки и проверки: около 5 часов.
